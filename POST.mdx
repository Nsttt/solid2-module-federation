Solid 2.0 went stable on November 16, and the headline feature is one sentence long: async lives in the reactive graph now.

```tsx
const user = createMemo(() => fetchUser(props.id));
```

That's it. A memo returns a Promise, everything downstream waits for it, a `<Loading>` boundary covers the first load, and `isPending` tells you when a newer answer is on its way. `createResource`, `startTransition`, `batch`, `on`, `produce` and `createComputed` are all gone, because the graph already knows how to do their jobs.

The whole pitch rests on the graph knowing the shape of your app. Module Federation's whole pitch is that your app doesn't have one shape: a host here, a remote there, each built by a different team, on a different compiler run, deployed whenever it wants.

So I wanted to know what happens when one Solid 2.0 transition has to cross three bundles that have never seen each other's source code.

Short answer: it works, and it's kind of delightful to watch. Get one line of config wrong and nothing works at all.

## The demo: a dropdown split three ways

The [announcement post](https://www.solidjs.com/blog/solid-2-0-the-long-hold/) shows off the new model with an async cascading dropdown. Pick a state, the cities refetch, the selected city resets to the first one. No effects syncing state, no loading flags. I took that exact example and pulled it apart across three [Rsbuild](https://rsbuild.rs) apps:

- `shell`, on port 3000, is the host. It owns the page and the only `<Loading>` boundary.
- `places`, on port 3001, exposes the location model and the picker UI.
- `forecast`, on port 3002, exposes a component that takes a `city` prop and fetches a forecast for it.

The model in `places` is the announcement's code, lifted out of the component so another bundle can create it:

```ts
// apps/places/src/location.ts
export function createLocation(country = 'US') {
  const states = createMemo(() => getStates(country));
  const [selectedState, setState] = createSignal(() => states()[0]);
  const cities = createMemo(() => getCities(selectedState()));
  const [selectedCity, setCity] = createSignal(() => cities()[0]);

  return { states, selectedState, setState, cities, selectedCity, setCity };
}

export const LocationContext = createContext<LocationModel>();
```

`createSignal(() => cities()[0])` is my favorite small thing in 2.0. It's a writable derived signal: it resets when its source changes, and the user can still overwrite it. In 1.x that was a signal plus an effect plus a bug report.

The `forecast` remote is even smaller, and has no idea it's async from anyone else's point of view:

```tsx
// apps/forecast/src/Forecast.tsx
export default function Forecast(props: { city: string }) {
  const forecast = createMemo(() => fetchForecast(props.city));

  return (
    <section class={['panel', 'forecast', { stale: isPending(forecast) }]}>
      <h2>{forecast().city}</h2>
      {/* ... */}
    </section>
  );
}
```

No `<Loading>` in there. That's the point.

The shell stitches it together:

```tsx
// apps/shell/src/App.tsx
import { createLocation, LocationContext } from 'places/location';

const LocationPicker = lazy(() => import('places/LocationPicker'));
const Forecast = lazy(() => import('forecast/Forecast'));

export default function App() {
  const location = createLocation();

  return (
    <LocationContext value={location}>
      <Loading fallback={<Skeleton />}>
        <LocationPicker />
        <Forecast city={location.selectedCity()} />
      </Loading>
    </LocationContext>
  );
}
```

Count the boundaries this crosses. The shell creates reactive state whose code lives in `places`. It provides a context that `places` consumes. It passes a value from `places` as a prop into `forecast`. And one `<Loading>` in the shell has to wait on two lazy remote components, the async memos inside `places`, and the async memo inside `forecast`.

## One transition, three bundles

Here's the page after it settles:

![The shell rendering the picker from places and the forecast from forecast](./images/one-graph-three-bundles-settled.png)

Now switch the state from California to Texas. The fake APIs take 700ms for cities and 900ms for the forecast, and the forecast can't start until the city is known, so the whole change takes about 1.6 seconds. Here's what the page shows during that time:

![Texas selected, the city select disabled, San Francisco's forecast dimmed](./images/one-graph-three-bundles-holding.png)

The old answer stays on screen. The city select is disabled because `isPending(location.cities)` is true over in `places`. The forecast is dimmed because `isPending(forecast)` is true over in `forecast`. No skeleton and no half-updated page. Solid calls this a hold, and the release post is named after a diagnostic, `LONG_HOLD`, that fires when one drags on too long.

Then the new city list and the Austin forecast land together. I drove this with Playwright, sampling the DOM every 150ms during the change, and never once caught a Texas city list sitting next to a California forecast. Three bundles, compiled separately, served from three origins, and the user sees one atomic update.

Nothing in that code coordinates it. There's no transition API to call and no shared loading store. The graph saw a write that triggered async work, held everything downstream of it, and committed when the last piece landed. It just doesn't care which bundle a node was compiled in.

As long as it's one graph.

## The one line that matters

Every app in the repo imports the same `shared` config:

```ts
const solid = { singleton: true, requiredVersion: '^2.0.0' } as const;

export const sharedSolid = {
  'solid-js': solid,
  '@solidjs/web': solid,
  '@solidjs/signals': solid,
};
```

If you've done federation with React, this looks familiar: `react` and `react-dom` as singletons, done. Solid 2.0 has one more name to get right. The scheduler, the owner tree, context lookup and transition bookkeeping all live in module state inside `@solidjs/signals`, a dependency of `solid-js` that you never import yourself. I list it by name so I pick the version that gets shared. Otherwise the lockfile picks it.

To see what the config is protecting, the repo has a script that breaks it on purpose:

```bash
pnpm dev:unshared
```

That drops the `shared` block from `forecast`, so it bundles a private copy of Solid. Here's the result:

![The page stuck on the loading skeleton](./images/one-graph-three-bundles-unshared.png)

Forever. And the console says:

```
You appear to have multiple instances of Solid: a signal or store from one copy was read
inside a computation of another, so the read is not tracked and will not update.

[PENDING_ASYNC_UNTRACKED_READ] Reading a pending async value directly in <Forecast>.
Async values must be read within a tracking scope (JSX, a memo, or an effect's compute function).

[REACTIVITY_HALTED] An uncaught error halted the reactive system.
No further updates will be processed.
  in <App> › <LocationContext> › computed › <Loading> › children › <Forecast> › computed
```

Look at what happened. `Forecast`'s memo was created by the copy of Solid inside `forecast`. The JSX reading it runs inside an owner created by the shell's copy. Each copy has its own idea of "the current tracking scope", so from the memo's side, nobody is tracking. A pending read outside a tracking scope is an error in 2.0, the error escapes every boundary because the boundary belongs to the other copy, and the reactive system halts.

The cheap version of this bug, two Reacts on a page, usually gets you a confusing hooks error. In Solid 2.0 it's two graphs, and async can't cross between graphs.

## Diagnostics are great, and they're not about your config

I want to give Solid real credit here. That first warning is spot on. It names the problem and tells you to check how every package resolves `solid-js`. It exists because `@solidjs/signals` registers every copy it evaluates on `globalThis.Solid$$copies` in development builds. The shell's footer reads that counter, so the healthy setup shows "1 copy of Solid" with three bundles on the page. Production builds strip the counter.

The second diagnostic is the trap. `PENDING_ASYNC_UNTRACKED_READ` points at `<Forecast>`, and the fix it suggests is reading the value inside a tracking scope. The code already does that. If an agent, or a tired human, skips the first warning and follows the repair guide for the second, they'll go rewrite a component that has nothing wrong with it.

Solid 2.0 is explicitly [built to be written by agents](https://www.solidjs.com/blog/solid-2-0-the-long-hold/), with stable codes and repair guides shipped in `node_modules/solid-js/skills`. That works well when the bug is in the code the agent can see. A federation misconfiguration lives somewhere else entirely: in a build config, possibly in a repo owned by another team. So when you see `multiple instances of Solid`, fix the shared config before anything else, and treat every diagnostic after it as noise until that's done.

## The boring bits that bit me

Two more things worth knowing before you wire this up yourself.

**Remotes need `assetPrefix: 'auto'`.** Out of the box, the remotes' `mf-manifest.json` said `publicPath: "/"`, so in a production build the shell on `:3000` would have requested `places` chunks from `:3000`. Setting `output.assetPrefix` and `dev.assetPrefix` to `'auto'` makes the remote resolve chunks relative to wherever its manifest was served from.

**Don't type remotes with tsconfig `paths`.** It's the obvious move: map `places/*` to `../places/src/*` and TypeScript is happy. But Rsbuild honors `paths` as resolve aliases, so the shell would quietly bundle the remote's source instead of loading it through federation. Everything would still work, and none of it would be federated. I hand-wrote declarations with type-only `import()`s instead, which never reach the bundler.

The tooling is fresh, too. `@rsbuild/plugin-solid@2.0.0`, the version that targets Solid 2.0, was published the morning I built this. Rsbuild was the easy choice because `@module-federation/rsbuild-plugin` is the most complete MF integration out there, but `@solidjs/vite-plugin@3` with `@module-federation/vite` should work on the same principle.

## So, should you federate Solid 2.0?

If you were already doing micro-frontends, Solid 2.0 is a better fit than 1.x was. Async in the graph means a remote can be async without exporting a loading state, a resource, or a convention every host has to know about. It hands back a component, and the host's boundary handles the rest. I've wanted that contract from federation for a long time.

The price is the same one federation always charges, just with higher stakes: everyone has to agree on the runtime. In Solid 2.0 the shared runtime includes the scheduler, and the scheduler decides what your user sees and when.

> Share `@solidjs/signals`, or you don't have one app. You have three apps taking turns on the same `<div>`.

The whole demo, including the `pnpm dev:unshared` script that breaks it, is on GitHub. Clone it, open `:3000`, pick Texas, and watch three bundles agree on one thing.
